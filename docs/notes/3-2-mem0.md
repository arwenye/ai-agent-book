## 实验出发点

memobase 手写实现中，semantic memory 的写入路径根本不存在，记忆提取完全靠手工调用。mem0 实验的出发点是：**把记忆提取和去重交给成熟框架**，观察框架替你做了什么决策，以及它的代价是什么。

mem0 v3 的核心设计是 **ADD-only**：所有记忆只追加，不主动删除，通过时间感知混合检索（semantic + BM25 + time）优先返回当前事实。观察重点是这种设计在"用户搬家/更正错误"场景下的实际表现。

```
    └── VectorStore     — 本地 Chroma（ANN 检索）
```

## 逐层代码理解

### KimiK3Client（agent.py）

纯封装层，`generate()` 加了 `@retry(stop=stop_after_attempt(3))` 重试，`agenerate()` 是 `asyncio.to_thread` 包装的异步版本，底层还是同步调用。

### Mem0Agent._init_memory()（agent.py 第 143 行）

mem0 的配置在这里组装，关键点：

```python
mem0_config = {
    "llm": {
        "provider": "openai",
        "config": {
            "api_key": ...,
            "openai_base_url": ...,   # 指向 Kimi
            "model": ...,
            "temperature": 1,          # K3 推理模型只接受 temperature=1
            "max_tokens": max(..., 2048),
        }
    },
    "vector_store": { "provider": "chroma", "config": { "path": "./data/chroma_db" } },
    "embedder": {
        "provider": "openai",
        "config": {
            "model": ...,
            "api_key": ...,            # 必须显式传，否则找 OPENAI_API_KEY 报错
            "openai_base_url": ...,    # 指向本地 Embedding 服务
        }
    }
}
```

**两个 LLM 调用是独立配置的：**
- `llm` 块 → Kimi（对话生成 + mem0 内部事实提取都走这里）
- `embedder` 块 → Embedding 服务（向量化，不能用 OpenRouter，因为 OpenRouter 没有 embeddings endpoint）

### process_turn() 一次对话的完整流程

```
用户输入
    │
    ▼
memory.search(query, user_id, top_k=5)
    → Embedder 把 query 向量化
    → Chroma ANN 检索相关记忆
    → 返回 top-5 记忆文本
    │
    ▼
拼 prompt（system + 记忆上下文 + 最近 10 轮历史 + 用户输入）
    │
    ▼
KimiK3Client.generate(messages)
    → 第一次 LLM 调用：生成对话回复
    │
    ▼
memory.add(user_msg + assistant_reply, user_id)
    → 第二次 LLM 调用（mem0 内部，对用户不可见）：
      Kimi 读取这轮对话，提取值得记住的事实
    → Embedder 向量化提取出的事实
    → 写入 Chroma（ADD-only，不删旧记录）
```

### 两次 LLM 调用的成本差异

这是 mem0 实验与手写实现最大的成本差异：

| 调用 | 触发时机 | 是否可见 | token 量 |
|------|----------|----------|----------|
| `KimiK3Client.generate()` | 每次对话 | ✅ 你能看到 | 对话长度 |
| `memory.add()` 内部提取 | 每次对话 | ❌ mem0 黑箱 | 额外消耗，取决于 mem0 实现 |

### main.py 的模式

## ADD-only 的实际含义

```bash
# 写入第一条
python main.py --mode memory --op add --text "我住在北京" --user-id u1

# 写入更新
python main.py --mode memory --op add --text "我搬到上海了" --user-id u1

# 查询
python main.py --mode memory --op get-all --user-id u1
# → 两条记录都存在：北京 + 上海

python main.py --mode memory --op search --query "用户住在哪里" --user-id u1
# → 两条都可能返回，时间权重让"上海"排名更高
```

旧事实不删除，只靠时间权重压制。检索词如果更匹配旧事实，旧事实仍可能排到前面。

## 检验题回答

**Q3：Mem0 ADD-only 在"用户更正错误信息"时出什么问题？**

旧的错误事实不会被删除，只追加新事实。两条并存，检索时都可能被返回。时间权重让新事实排名更高，但旧事实不消失——当检索词恰好更匹配旧事实时，仍可干扰回答。

**Q4：用户说"我上次告诉你我住北京，那是错的，我一直住上海"——mem0 如何处理？**

mem0 ADD-only 策略：追加"用户一直住上海"，北京的记录不删除，两条并存。时间权重优先上海，但北京未消失。需要手动 `op delete` 才能删除旧记录。

**Q6：Chroma 的查询复杂度，谁先出问题？**

Chroma ANN 搜索 O(log n)，向量操作本身不是瓶颈。真正的瓶颈是 Embedder：
- 每次 `memory.add()` 写入都要调 Embedding API（网络延迟）
- 每次 `memory.search()` 检索也要调 Embedding API vectorize 查询

mem0 在网络/成本上先出问题，不是在数据量上。对比手写实现（字符串匹配，O(n) 全遍历），手写在数据量大时先卡，mem0 在 API 调用成本上先出问题。

**Q7：替换本地 embedding 模型，改哪里？**

修改 `config.py` 的 `Mem0Config` 加 `embedding_api_key` / `embedding_base_url` 字段（已改），`agent.py` 的 embedder 块传入这两个值（已改），`.env` 配置对应的服务地址。OpenRouter 覆盖不了 embedder——OpenRouter 没有 embeddings endpoint，`config.py` 注释里明确说明了这一点。

**Q8：上线选哪个方案？**

mem0（本地后端）适合**有本地 Embedding 服务 + 需要跨会话持久记忆**的场景。

优势：事实提取自动化，ADD-only 实现简单，多用户隔离开箱即用。  
风险：强依赖 Embedding 服务可用性；ADD-only 对矛盾信息处理较弱；mem0 内部提取 LLM 的 token 消耗不透明。

如果业务对记忆准确性要求极高（金融/医疗），需要在 `memory.add()` 后检查返回的 `added_memories`，对可疑的更新做二次确认，不能完全信任框架的自动决策。
